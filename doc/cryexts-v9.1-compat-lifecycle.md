# CRYEXTS v9.1 兼容治理与生命周期规则

## 1. v9.1 的定位

`v9.0` 解决的是：

```text
把部署基线固定下来
```

而 `v9.1` 要解决的是下一件必须收口的事：

```text
把版本治理、兼容规则、升级回退规则固定下来
```

一句话定义：

```text
v9.1 = CRYEXTS 的兼容治理与生命周期基线版本
```

它不新增 on-disk 结构，
而是正式回答下面几个问题：

- project version 和 on-disk format version 到底是什么关系
- 当前推荐的新镜像格式到底是哪条线
- 什么改动可以不 bump format
- 什么改动必须 bump format
- 旧镜像如何升级
- 升级失败后如何回退

## 2. 为什么现在先做 v9.1

到当前为止，仓库里已经同时存在两套“版本语义”：

### 第一套：项目阶段版本

例如：

- `v7.0`
- `v8.4`
- `v9.0`
- `v9.1`

它们表达的是：

```text
当前这轮工程工作在解决什么问题
```

### 第二套：on-disk format version

当前代码可识别：

- `V3`
- `V4`
- `V5`
- `V6`

来自：

- [cryexts_fs.h](/D:/Carl/cryptext4/cryexts/cryexts_fs.h:12)
- [super.c](/D:/Carl/cryptext4/cryexts/super.c:112)
- [tools/cryextsck.c](/D:/Carl/cryptext4/cryexts/tools/cryextsck.c:492)

它们表达的是：

```text
镜像磁盘布局和 feature 语义版本
```

如果这两套版本不分开治理，
后面很容易出现三个问题：

1. 文档版本在前进，但磁盘格式含义说不清
2. 新代码能挂旧镜像，但推荐口径不明确
3. 后面真的要改格式时，不知道什么情况下该 bump

所以 `v9.1` 的目标不是加新功能，
而是先把：

```text
版本怎么管理
+ 兼容怎么承诺
+ 升级怎么执行
+ 回退怎么止损
```

这四件事写成规则。

## 3. 当前代码里的现实基线

`v9.1` 不是空想规则，
它必须建立在当前代码现实之上。

## 3.1 当前可识别的格式版本

当前内核挂载和 `cryextsck` 都接受：

- `V3`
- `V4`
- `V5`
- `V6`

也就是说，当前真实支持边界至少是：

```text
代码可识别版本 = V3 ~ V6
```

## 3.2 当前默认版本宏

[cryexts_fs.h](/D:/Carl/cryptext4/cryexts/cryexts_fs.h:17) 当前仍然定义：

```c
#define CRYEXTS_VERSION CRYEXTS_VERSION_V5
```

同时 [tools/mkfs.cryexts.c](/D:/Carl/cryptext4/cryexts/tools/mkfs.cryexts.c:391)
到 [tools/mkfs.cryexts.c](/D:/Carl/cryptext4/cryexts/tools/mkfs.cryexts.c:439)
也表明：

- `mkfs` 默认起步仍然是 `V5`
- 某些 feature 组合会把 `fs_version` 提升到 `V6`

这就意味着当前现实是：

```text
代码主线已经围绕 V6 在工程化，
但默认创建口径还没有完全收口到 V6
```

`v9.1` 不一定现在就改代码默认值，
但必须把治理规则先定下来。

## 3.3 当前主线 feature 现实

当前代码已存在并参与真实语义的主线能力包括：

- block groups / multi-GDT
- journal v2
- metadata checksum
- policy table / policy-aware encryption
- dir index
- extent tree
- large xattr

这些已经不是“预留位”，
而是当前推荐主线的一部分。

## 4. v9.1 要固定的四条规则

## 4.1 规则一：先分清两种版本

`v9.1` 明确规定：

### project version

作用：

- 表达当前工程迭代阶段
- 表达本轮交付目标
- 不直接等于磁盘格式版本

例子：

- `v9.0` 是部署基线
- `v9.1` 是兼容治理

### format version

作用：

- 表达 superblock 里的 on-disk 格式代际
- 表达某些不兼容结构边界

例子：

- `V5`
- `V6`

这条规则可以浓缩成一句话：

```text
项目版本前进，不等于磁盘格式一定前进
```

## 4.2 规则二：当前推荐格式主线固定为 V6

`v9.1` 建议把当前推荐主线正式固定为：

```text
recommended format baseline = V6
```

原因不是“看起来高级”，
而是当前已经落地的主线能力，本质上就是围绕 `V6` 收口的：

- journal v2 需要 `V6`
- large xattr 属于 `V6` 时代主线
- `Version 7` 的 raw-device / multi-GDT demo 主线也围绕 `V6`

所以 `v9.1` 的治理口径应是：

### 新创建镜像

推荐：

```text
以 V6 主线为准
```

### 历史镜像

继续识别：

- `V3`
- `V4`
- `V5`
- `V6`

但推荐口径不同：

- `V3/V4`：历史兼容线
- `V5`：过渡兼容线
- `V6`：当前推荐主线

## 4.3 规则三：能不 bump format，就不 bump

这是 `v9.1` 最重要的治理原则。

如果一个改动满足下面情况之一：

- 只是文档变更
- 只是脚本变更
- 只是 smoke / inspect / fsck 能力补强
- 只是 mount-time runtime 行为补强
- 只是 repair 策略补强
- 只是默认参数、推荐流程、部署基线调整

那么默认规则是：

```text
不 bump on-disk format version
```

因为这些改动本质上不改变：

- superblock 结构含义
- inode 磁盘字段含义
- feature bit 语义
- extent / dir index / xattr / policy table 布局

也就是说：

```text
工程版本可以继续从 v9.1 -> v9.2 -> v9.5 往前走，
但 format 仍然可以稳定停在 V6
```

## 4.4 规则四：真正改结构时才 bump format

下面这些情况，才进入“必须认真考虑 bump format”的范围：

### A. superblock 核心字段语义变化

例如：

- 已有字段改含义
- 关键字段位置/大小变化
- 同一个字段被复用成新语义

### B. group descriptor / inode / dirent / xattr / extent 的持久格式变化

例如：

- 现有结构体字段布局变化
- 解析规则变化且旧代码无法安全识别
- 旧镜像和新镜像会被混读误判

### C. 已公开 feature bit 语义变化

例如：

- 旧 bit 不再表示原来的能力
- 旧 bit 被拿去表达另一种含义

### D. 旧代码挂载新镜像会有静默误判风险

这是最关键的一条。

只要出现下面这种情况：

```text
旧代码可能“看起来能挂”，
但实际上会按错误语义解释新镜像
```

那就应该优先：

```text
新增新 feature 位
或者 bump format
```

而不是偷改旧语义。

## 5. v9.1 兼容承诺分层

`v9.1` 建议把兼容承诺分成三层，
避免“一句兼容”说得太满。

## 5.1 识别兼容

含义：

```text
新代码能识别这个版本/feature 组合
```

当前建议：

- `V3 ~ V6` 都保持识别兼容

## 5.2 运维兼容

含义：

```text
新代码不仅能识别，
而且还能继续用 fsck / inspect / 基础挂载路径处理
```

当前建议：

- `V5 / V6` 应作为重点运维兼容对象
- `V3 / V4` 保留基础识别和历史样本价值

## 5.3 推荐创建兼容

含义：

```text
今天创建新镜像时，官方推荐用哪条格式线
```

当前建议唯一主线：

```text
V6
```

这样就把“能识别”和“推荐新建”拆开了，
不会再混成一句模糊的“都支持”。

## 6. 升级规则

这里的“升级”分两种情况，
必须分开理解。

## 6.1 第一类升级：代码升级，镜像不升级

这是当前最推荐、也是最现实的主线。

模型是：

```text
旧镜像
-> 新内核模块 / 新工具
-> 按原格式继续挂载、fsck、inspect
```

适用于：

- `V5 -> 新代码`
- `V6 -> 新代码`
- 历史回归样本 `V3/V4 -> 新代码`

推荐步骤：

1. 先备份镜像或原始分区
2. 用新 `cryextsck` 先离线检查
3. 确认 clean 或已知可恢复
4. 再挂载新模块
5. 挂载后先做低风险读写验证

这一类升级的重点是：

```text
升级的是代码，不是镜像格式
```

## 6.2 第二类升级：镜像升级到新推荐主线

这一类要更保守。

当前 `v9.1` 的建议口径是：

```text
没有成熟的 in-place format upgrader 之前，
不要承诺在线格式升级
```

也就是说，若将来你真要把旧格式镜像升级成新推荐格式，
当前最稳的办法仍应是：

1. 备份原镜像
2. 导出数据
3. 用推荐主线重新 `mkfs`
4. 回灌数据
5. 再跑 `fsck + smoke`

这很朴素，但它是最小风险路径。

`v9.1` 不应该为了“看起来高级”，
现在就承诺一个还没真正做完的在线升级器。

## 7. 回退规则

回退也要分清两种情况。

## 7.1 第一类回退：新代码回退到旧代码

如果镜像本身没有发生格式变化，
只是：

- 换了新模块
- 跑了新 smoke
- 改了新文档流程

那么原则上：

```text
回退的是代码，不是镜像
```

前提是：

- 镜像上没有启用旧代码不认识的新 feature 组合
- 没有进入旧代码无法安全处理的状态

## 7.2 第二类回退：新建主线镜像回退到旧工具链

如果已经创建或写入了更高主线要求的镜像，
那就必须保守处理。

例如：

- 新镜像带 `V6` 特性
- 旧工具只按 `V5` 口径处理

这时 `v9.1` 的规则应是：

```text
不要假设“旧代码也许还能挂”
```

而应该：

1. 先离线检查旧代码是否显式支持
2. 如果不确定，就不要挂
3. 需要回退时，优先恢复备份或重建测试镜像

## 7.3 当前不提供自动降级承诺

`v9.1` 应明确写死：

```text
当前不承诺自动 format downgrade
```

原因很简单：

- 自动降级天然风险更高
- 很容易把“可识别”误说成“可逆转换”
- 当前项目阶段不值得先做这个复杂度

## 8. feature 位治理规则

这部分要尽量简单，不玩复杂政策。

## 8.1 已公开语义的旧位不改含义

一旦一个 feature 位已经被主线代码和文档公开承认，
后续规则就是：

```text
不复用
+ 不漂移
+ 不偷改
```

如果真有新需求，优先：

1. 新增新位
2. 或者 bump format

而不是修改旧位含义。

## 8.2 `NEEDS_RECOVERY` 归类为状态位

`NEEDS_RECOVERY` 最容易被误解成“结构能力位”。

`v9.1` 应继续保持下面这个口径：

```text
它是运行时 / 恢复状态位，
不是长期格式能力主线的一部分
```

这有助于后续做 recovery / fsck / replay 规则时不混淆。

## 8.3 推荐 profile 的 feature 组合要固定

`v9.1` 应把推荐创建 profile 理解成：

```text
V6
+ journal v2
+ block groups
+ policy table
+ dir index
+ extent tree
+ metadata checksum
+ large xattr
```

后面如果继续演进，
也优先在这条组合上做主线验证。

## 9. 最小升级 / 回退手册

这里不搞复杂流程，
只给最小可执行版本。

## 9.1 推荐升级流程

适用场景：

- 新版模块 / 新版工具上线前

步骤：

1. 备份 image 或专用测试分区
2. 保存当前 `dmesg`、`cryextsck`、inspect 输出
3. 升级模块和工具
4. 先离线跑 `cryextsck`
5. 再挂载验证
6. 先做小范围读写
7. 再跑对应 smoke / demo

## 9.2 推荐回退流程

适用场景：

- 新代码行为异常
- 新流程验证失败

步骤：

1. 立刻停止继续写入
2. 保存现场信息
3. 用当前 `cryextsck` 先离线检查
4. 如果要回退代码，先确认镜像未进入旧代码不识别的组合
5. 最稳妥路径仍然是恢复备份镜像

## 9.3 原则

可以把 `v9.1` 的升级/回退原则压成一句话：

```text
升级优先“换代码不换格式”，
回退优先“恢复备份不赌兼容”
```

## 10. v9.1 对后续代码调整的约束

虽然这一版先不动代码，
但它已经给后面代码改动加了约束。

## 10.1 `mkfs` 默认主线最终应与推荐格式一致

当前现实是：

- 默认宏还是 `V5`
- 工程主线已经围绕 `V6`

`v9.1` 先把口径定下来：

```text
后续代码默认创建行为，
应逐步收口到推荐主线 V6
```

这次先不强行改，
但方向不能再模糊。

## 10.2 mount / fsck / inspect 的支持边界要保持一致

后续如果支持矩阵有变化，
应该一起检查：

- `super.c`
- `cryextsck.c`
- inspect 工具口径
- 文档口径

避免出现：

```text
内核说支持
fsck 说不支持
文档又说另一套
```

## 10.3 真要改格式，先写治理说明再写代码

后面如果有任何版本真的准备引入 `V7` on-disk format，
`v9.1` 的规则是：

```text
先写清楚为什么必须改
+ 改哪些持久结构
+ 旧镜像如何处理
+ 回退是否可能
```

然后再开始动代码。

## 11. v9.1 推荐验收标准

我建议把 `v9.1` 完成定义成下面五件事：

### 11.1 外部读者能分清 project version 和 format version

### 11.2 当前推荐创建主线明确固定为 V6

### 11.3 “什么情况下不 bump，什么情况下必须 bump”有书面规则

### 11.4 升级流程和回退流程有最小手册

### 11.5 后续格式演进不再建立在口头约定上

## 12. 一句话总结

如果说：

- `v9.0` 解决的是“怎么部署”

那么：

```text
v9.1 解决的是：
怎么治理版本、怎么承诺兼容、怎么执行升级和怎么安全回退
```
