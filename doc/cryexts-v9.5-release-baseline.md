# CRYEXTS v9.5 发布门槛与性能基线

## 1. v9.5 的定位

`v9.0` 解决的是：

```text
把部署基线固定下来
```

`v9.1` 解决的是：

```text
把兼容治理和升级回退规则固定下来
```

`v9.2` 解决的是：

```text
把单次 smoke 推进成可重复执行的 soak 主线
```

`v9.3` 解决的是：

```text
把恢复与 repair 分流规则固定下来
```

`v9.4` 解决的是：

```text
把健康检查和 inspect 使用顺序固定下来
```

而 `v9.5` 要解决的是 `Version 9` 最后一个收口问题：

```text
什么时候算“这一版可以发”
+ 发布前最少要通过什么
+ 稳定性至少要拿出什么证据
+ 性能至少要给出什么观察
```

一句话定义：

```text
v9.5 = CRYEXTS 的发布门槛与最小性能基线版本
```

## 2. 为什么现在先做 v9.5

到 `v9.4` 为止，
CRYEXTS 已经把下面几件事基本收起来了：

- 部署路径固定
- 兼容治理固定
- soak 主线固定
- recovery / repair 规则固定
- 健康检查顺序固定

现在最缺的不是再加一份说明，
而是把它们收成一条最终发布口径：

```text
什么叫“这一版通过了”
```

否则后面继续推进时，
还是很容易回到老问题：

1. 每次发布标准不一样
2. 这次看 smoke，下次看 demo，再下次只看感觉
3. 稳定性和性能结论写法没有统一口径

所以 `v9.5` 的目标很简单：

```text
把前面文档沉淀成一张可执行的发布门槛表
```

## 3. v9.5 不做什么

为了防止继续发散，`v9.5` 明确不做：

- 论文级 benchmark 体系
- 多平台大规模性能对比
- 自动性能看板
- 完整长期 soak 平台
- 生产级 SLA 承诺
- 新 on-disk feature

原因很简单：

```text
当前最短路径不是“做一整套性能平台”，
而是“先把最小可重复的发布门槛固定下来”
```

## 4. v9.5 的三类交付

`v9.5` 建议只收三类东西：

1. 发布门槛
2. 稳定性门槛
3. 最小性能基线

## 5. 发布门槛

发布门槛回答的是：

```text
这版能不能作为一个“完成版本”对外说明
```

## 5.1 构建门槛

至少要满足：

- `make` 成功
- `cryexts.ko` 可生成
- `mkfs.cryexts` 可生成
- `cryextsck` 可生成
- inspect 工具可生成

如果连构建都不稳定，
这版就不应进入后面的 smoke / soak / benchmark 讨论。

## 5.2 基础功能门槛

至少要满足：

- 基础 image 路径可 `mkfs -> mount -> write -> umount -> fsck`
- remount 路径成立
- `cryextsck` clean
- 基础目录 / 文件 / rename / link 路径成立

这部分的意义是：

```text
先证明主线功能没有回退
```

## 5.3 结构能力门槛

至少要满足：

- extent tree 路径可验证
- sparse file 路径可验证
- dir index 路径可验证
- xattr 路径可验证
- multi-GDT 路径可验证

这部分不是为了“把所有脚本都跑一遍”，
而是为了确认当前主线结构能力没有失守。

## 5.4 恢复能力门槛

至少要满足：

- journal replay 路径可验证
- orphan cleanup 路径可验证
- `cryextsck` 能稳定给出一致结果
- `v9.3` 定义的低风险 `--repair` 边界没有被突破

这部分的目标是：

```text
不是只会正常跑，
而是异常路径也有基本闭环
```

## 5.5 部署路径门槛

至少要满足：

- image demo 可通过
- encrypted demo 可通过
- raw-device demo 在专用测试介质上可通过

同时必须遵守：

- 先 image
- 再 encrypted
- 最后 raw-device

这和 `v9.0` 的部署顺序保持一致。

## 5.6 文档门槛

至少要满足：

- 当前版本说明已补
- 风险边界没有写过头
- 支持边界没有写模糊
- 恢复与观测口径和前文一致

如果代码过了，但文档口径互相打架，
也不应视为真正完成。

## 6. 稳定性门槛

稳定性门槛回答的是：

```text
这版不是只跑过一次，
而是有最小重复运行证据
```

## 6.1 quick soak 门槛

至少应有一条开发期快速回归线：

- 以 image 为主
- 包含 mount / 写删 / fsck
- 轮数不需要很大

它的用途是：

```text
每次代码改完先确认没有马上炸
```

## 6.2 full soak 门槛

发布前至少应有一条更完整的 soak：

- mount / umount 循环
- 写删循环
- replay / fsck 循环
- 必要时包含 raw-device 循环

关注点至少包括：

- `cryextsck` 是否保持 clean
- 是否出现 replay pending 残留
- 是否出现 `Structure needs cleaning`
- `dmesg` 是否出现明显错误

## 6.3 raw soak 门槛

如果这一版要对外强调真实设备路径，
则 raw-device 不能只过一次 demo。

至少应该有：

- 专用测试介质
- 多轮 mount / umount / fsck
- 一次以上 remount 验证

它的目标不是“压力极限”，
而是：

```text
证明 raw-device 不是一次性样品
```

## 7. 最小性能基线

`v9.5` 的性能目标不是“跑分好看”，
而是：

```text
至少让同一版本之间有可重复的观察口径
```

## 7.1 为什么这里只做最小性能基线

原因很简单：

- 当前项目仍是实验 / 评估主线
- 还不到要做完整性能平台的时候
- 但如果完全没有性能观察，后面就无法比较回归

所以 `v9.5` 建议只固定最小场景。

## 7.2 建议固定的最小性能场景

至少保留下面几类场景：

### A. 顺序写大文件

回答：

```text
大文件主线是否基本可用
```

### B. 顺序读大文件

回答：

```text
读路径是否有明显退化
```

### C. 小文件批量创建

回答：

```text
inode / dir index / allocator 主线是否有明显异常
```

### D. 多目录项扫描

回答：

```text
目录路径和索引路径是否基本成立
```

### E. remount 后一致性检查耗时

回答：

```text
恢复和离线检查主线是否出现明显异常增长
```

## 7.3 建议固定的观察条件

为了避免每次结论都不可比，
建议至少固定：

- 测试介质
- 镜像大小或分区大小
- 是否启用 `KEY`
- 是否走 image 还是 raw-device
- 大文件大小
- 小文件数量

也就是说，性能观察至少要做到：

```text
条件可复述
+ 命令可复述
+ 结果可复述
```

## 7.4 结果写法建议

`v9.5` 不要求复杂表格系统，
但建议每次至少记录：

- 场景
- 测试条件
- 结果摘要
- 是否与上一版相比明显变差

例如可以写成：

```text
image / non-encrypted / 1GiB sequential write:
本版可稳定完成，未观察到明显回退
```

重点不是绝对数字多漂亮，
而是：

```text
有没有明显回退
有没有异常抖动
能不能重复做出来
```

## 8. 建议的最小发布模板

`v9.5` 最终最好收成一张最小发布记录。

建议模板至少包含：

## 8.1 基本信息

- 版本号
- 测试时间
- 测试环境
- 内核版本
- image / raw-device / encrypted 是否覆盖

## 8.2 构建结果

- `make` 是否通过
- 核心工具是否生成

## 8.3 smoke 结果

- 通过了哪些关键 smoke
- 哪些 smoke 没跑
- 没跑的原因是什么

## 8.4 soak 结果

- quick soak 结果
- full soak 结果
- raw soak 结果

## 8.5 恢复结果

- replay 路径是否验证
- orphan cleanup 是否验证
- `--repair` 是否仍保持低风险边界

## 8.6 健康检查结果

- `cryextsck` 是否 clean
- 关键 inspect 是否符合预期
- 是否出现异常 `dmesg`

## 8.7 性能观察

- 大文件读写
- 小文件创建
- 目录扫描
- 是否观察到明显回退

## 8.8 已知限制

- 本版仍然有哪些限制
- 哪些场景仍不建议使用

## 9. 建议的发布判定规则

为了避免“差不多就发”，
`v9.5` 可以把判定规则压成下面三档。

## 9.1 可以发布

满足：

- 构建通过
- 关键 smoke 通过
- 至少一条 soak 通过
- 恢复路径验证通过
- 文档口径一致
- 没有明显未解释的健康检查异常

## 9.2 只能内部验证

满足：

- 构建通过
- 基础 smoke 通过
- 但 soak 还不够
  或 raw-device 结果不稳定
  或性能观察不完整

这类版本可以继续内部推进，
但不建议作为“阶段完成版”对外说满。

## 9.3 不应发布

出现以下任一情况：

- 构建不稳定
- `cryextsck` 结果不一致
- replay / recovery 路径明显回退
- soak 出现未解释异常
- 文档与实际行为明显不一致

## 10. Version 9 MVP 收口定义

`v9.5` 可以把 `Version 9 MVP` 最终收成下面这句话：

```text
CRYEXTS 已经不只是“能演示的实验文件系统”，
而是具备：

1. 固定部署主线
2. 固定兼容治理规则
3. 固定恢复 / repair 手册
4. 固定健康检查入口
5. 固定发布门槛与最小稳定性 / 性能基线
```

这也是 `Version 9` 和前面最大的区别：

```text
它开始像一条可持续演进的工程主线，
而不只是分散能力集合
```

## 11. v9.5 推荐验收标准

我建议把 `v9.5` 完成定义成下面五件事：

### 11.1 发布门槛固定

即知道：

- 什么必须过
- 什么可以暂缓
- 什么过不了就不该发布

### 11.2 soak 结果正式进入发布判断

而不是只看单次 smoke。

### 11.3 性能观察至少有最小口径

不要求豪华 benchmark，
但至少能比较、能回归、能解释。

### 11.4 文档和测试结果能收成一份发布记录

而不是散落在多条日志里。

### 11.5 `Version 9` 可以视为一个完整收口阶段

也就是：

```text
后面要继续往 v10 走时，
不需要再回头补“基础治理”这一层
```

## 12. 一句话总结

如果说：

- `v9.0 ~ v9.4` 分别解决了部署、兼容、稳定性、恢复、观测

那么：

```text
v9.5 解决的是：
把这些成果收成真正可执行的发布门槛，
并给 CRYEXTS 建立最小稳定性与性能基线
```
