# CRYEXTS v8.4 设计说明

## 1. v8.4 的定位

`v8.0` 解决的是：

```text
让仓库入口像一个公开项目
```

`v8.1` 解决的是：

```text
让格式边界和兼容边界说得清楚
```

`v8.2` 解决的是：

```text
让测试、恢复、排障矩阵组织清楚
```

`v8.3` 解决的是：

```text
让 demo 路径变成可复现、可执行的产品化入口
```

而 `v8.4` 要解决的，是 `Version 8` 里最后那条最现实的对外目标：

```text
commercial-evaluation-ready
```

一句话定义：

```text
v8.4 = CRYEXTS 的商用评估资料包基线版本
```

## 2. 为什么现在先做 v8.4

到当前为止，CRYEXTS 已经有：

- 核心文件系统语义
- multi-GDT 与真实设备 demo 路径
- 一套逐步完善的 smoke / inspect / fsck / repair 能力
- 一条逐渐清晰的开源、兼容、测试、demo 主线

也就是说，当前已经不再缺“能不能演示”。
现在更需要回答的是：

```text
如果别人想拿这个项目做内部技术评估、架构评估、风险评估，
我们要给他什么材料，才能让评估是可执行的、可解释的、边界清晰的
```

### 2.1 商用评估不是生产承诺

这件事必须先说死。

`commercial-evaluation-ready` 的意思是：

- 可以拿去做 PoC
- 可以拿去做技术路线讨论
- 可以拿去做内部风险评估
- 可以拿去做演示、对比、可行性验证

它不等于：

- 可以直接承载重要生产数据
- 可以直接做量产发布
- 已经完成生产级安全审计
- 已经具备长期兼容承诺与 SLA 承诺

所以 `v8.4` 的目标不是“证明已经可商用”，
而是：

```text
把“如何评估这个项目是否值得后续商用投入”这件事资料化
```

### 2.2 现在缺的不是技术点，而是“评估口径”

现在仓库里已经有很多技术文档，
但外部评估者通常更关心这些问题：

- 当前支持边界是什么
- 当前明确不支持什么
- 风险点有哪些
- 测试覆盖到哪里
- 恢复能力到哪里
- 加密能力的现实边界是什么
- 如果要继续投入商用，还差哪些工作

这些信息现在分散在很多文档里，
还没有收成一套“评估资料包”。

### 2.3 评估材料的价值在于“减少误解”

如果没有评估资料包，最容易发生两种误解：

#### 误解 A

别人以为：

```text
既然已经能 raw-device demo，
那就差不多等于可以上生产
```

这是危险的。

#### 误解 B

别人又可能以为：

```text
既然还不是 production-ready，
那就完全没有评估价值
```

这也不对。

所以 `v8.4` 的意义就是把中间这层讲清楚：

```text
它已经足够拿来评估，
但还不应该被描述成生产级文件系统
```

## 3. v8.4 主目标

`v8.4` 建议只做一件事：

```text
建立一套可对外交付的 CRYEXTS 商用评估资料包
```

拆开看，最少包含六类材料：

1. 支持边界说明
2. 已知限制说明
3. 风险声明
4. 测试覆盖说明
5. 稳定性 / 性能基线说明
6. 后续商用差距说明

## 4. v8.4 不做什么

为了防止范围继续发散，`v8.4` 明确不做：

- production-ready 承诺
- SLA 承诺
- 长期兼容承诺
- 完整性能 benchmark 体系
- 完整安全审计
- 正式灾备体系
- 大规模设备兼容验证
- 商业合同级材料

原因很简单：

```text
v8.4 做的是“可评估资料包”，
不是“可直接销售的产品交付包”
```

## 5. v8.4 要解决的六类问题

## 5.1 支持边界说明

这部分要回答：

```text
CRYEXTS 当前明确支持什么，不支持什么
```

建议至少写清楚下面几类边界。

### 支持的使用场景

建议明确写成：

- 研究
- 教学
- 体系结构验证
- 文件系统原型评估
- 专用测试设备
- demo / PoC / 内部评审

### 不建议的使用场景

建议明确写成：

- 重要生产数据
- 无备份环境
- 长期业务系统
- 合规要求严格的正式生产环境

### 支持的工程边界

建议明确说明：

- 当前主要验证环境是什么
- 当前主要验证路径是 image 还是 raw-device
- 当前哪些内核版本/发行版是主验证对象

这部分的目标是让评估者知道：

```text
哪些是当前项目真正站得住脚的边界
```

## 5.2 已知限制说明

这部分要回答：

```text
当前项目还有哪些明确的天花板、缺口和未完成项
```

建议至少覆盖下面几类。

### 恢复与一致性限制

- `cryextsck --repair` 只承诺低风险修补
- 不是所有损坏都能自动修
- mount-time replay 只覆盖已设计的 journal 路径

### 结构能力限制

- 当前 extent tree 仍然是 MVP 路线，不是无限层级成熟设计
- 目录索引仍然不是完整的多层 HTree
- xattr 扩展路径仍然是有限模型

### 安全与加密限制

- 当前有加密路径，但不等于完成生产级安全审计
- 当前加密实现不应被宣传成合规级安全产品能力

### 运维与兼容限制

- 当前支持边界依赖已验证环境
- 长期升级兼容策略还未完全冻结

这部分要尽量具体，不能只写“还有很多限制”。

## 5.3 风险声明

这部分要回答：

```text
如果有人现在就拿它做更重的事情，风险在哪里
```

建议风险至少分成三层。

### A 类：数据风险

- 原始块设备误操作风险
- 异常中断后的恢复边界风险
- repair 误用风险

### B 类：安全风险

- 加密能力不应被误解为已完成正式安全审计
- 密钥管理仍然属于工程化弱项之一

### C 类：演进风险

- 格式主线虽然逐渐清晰，但长期稳定 ABI/format policy 仍在收口中
- 某些历史兼容线未来可能只保留读取/检查，不再推荐新建

这部分的目标是：

```text
让评估者知道风险不是没有，
但风险是可以被识别和讨论的
```

## 5.4 测试覆盖说明

这部分要回答：

```text
你说项目可评估，有哪些测试证据支撑
```

建议按照 `v8.2` 的矩阵思路整理。

### 建议覆盖的测试类别

- 基础格式路径
- 结构能力路径
- 恢复路径
- 部署路径

### 至少应明确列出的关键测试

- `Version 6 MVP` smoke
- multi-GDT mount / fsck
- USB / raw-device demo
- journal replay / orphan cleanup
- extent tree / sparse file / dir index / xattr

### 需要说清楚的不是“有脚本”

而是：

```text
这些脚本 pass 后，分别证明了什么能力
```

也就是说，`v8.4` 的测试覆盖说明
应直接引用 `v8.2` 的测试矩阵成果，而不是重复发明。

## 5.5 稳定性 / 性能基线说明

这部分要回答：

```text
当前有没有最小的稳定性与性能证据
```

这里不要求完整 benchmark 体系，
但至少要有可以展示的基线。

### 稳定性基线建议内容

- 多次 `mount -> write -> umount -> remount`
- `fsck clean` 是否持续成立
- image 与 raw-device 两条路径的最小回归结果

### 性能基线建议内容

- 顺序写大文件的基本观测
- 稀疏文件场景的基本观测
- 目录项较多场景的基本观测

### 这部分的目标不是“证明性能多强”

而是：

```text
给评估者一个最小、可复现、可展示的性能/稳定性观察基线
```

## 5.6 后续商用差距说明

这部分非常关键。

它要回答：

```text
如果真的想继续往商用方向投入，
现在还差什么
```

建议至少明确列出下面几类差距。

### A 类：安全差距

- 完整安全审计
- 密钥生命周期管理
- 更清晰的攻击面分析

### B 类：性能差距

- 系统化 benchmark
- 长时间 soak test
- 多设备、多负载场景评估

### C 类：兼容与维护差距

- 长期格式演进策略
- 升级迁移策略
- 更正式的支持矩阵

### D 类：运维差距

- 更完整灾难恢复手册
- 更强 repair 策略
- 更清晰的现场排障闭环

这一步的价值在于：

```text
让“后续是否值得继续投入”变成可讨论的清单，
而不是抽象口号
```

## 6. v8.4 建议产出的资料包

`v8.4` 最终不应该只停在这份设计文档，
而应该至少沉淀出下面几份可交付材料。

## 6.1 `Known Limitations`

作用：

- 专门列当前限制
- 避免把限制埋在长文档里

建议内容：

- 数据恢复限制
- 结构能力限制
- 安全限制
- 兼容限制

## 6.2 `Support Boundary`

作用：

- 专门列当前支持边界

建议内容：

- 适合场景
- 不适合场景
- 推荐验证环境
- 推荐 demo 路径

## 6.3 `Evaluation Checklist`

作用：

- 给内部评估者一张检查单

建议内容：

- 构建是否通过
- 基础 smoke 是否通过
- image demo 是否通过
- raw-device demo 是否通过
- fsck / replay / orphan 路径是否验证
- 关键风险是否已理解

## 6.4 `Stability & Observation Note`

作用：

- 放最小稳定性/性能说明

建议内容：

- 观测环境
- 观测脚本
- 基本结果
- 不要过度宣传

## 6.5 `Commercial Gap Note`

作用：

- 专门列“离生产还有多远”

建议内容：

- 安全差距
- 性能差距
- 兼容差距
- 运维差距

## 7. v8.4 与前面版本的关系

`v8.4` 不应该脱离前面版本单独存在，
而是要复用前面已经整理好的成果。

### 依赖 `v8.0`

- 开源仓库入口
- 风险口径

### 依赖 `v8.1`

- 格式边界
- 兼容边界

### 依赖 `v8.2`

- 测试矩阵
- 恢复矩阵

### 依赖 `v8.3`

- demo profile
- demo 风险与排障口径

也就是说：

```text
v8.4 不是重新定义项目，
而是把 v8.0 ~ v8.3 的成果打包成“可评估材料”
```

## 8. v8.4 推荐实施顺序

建议按最小顺序推进：

1. 先写 `Support Boundary`
2. 再写 `Known Limitations`
3. 再写 `Evaluation Checklist`
4. 再写 `Stability & Observation Note`
5. 最后写 `Commercial Gap Note`

这个顺序的原因很简单：

- 先说清楚能干什么
- 再说清楚不能干什么
- 再说清楚怎么评估
- 最后再说离真正商用还差什么

## 9. v8.4 验收标准

`v8.4` 完成的最小标准建议定义为：

### 9.1 外部评估者能看懂当前定位

必须能清楚知道：

- 这是可评估项目
- 不是生产可用承诺

### 9.2 外部评估者能知道支持边界和限制

不再需要在很多文档里自己拼凑。

### 9.3 外部评估者能按清单执行一次 PoC 评估

包括：

- 构建
- smoke
- demo
- 恢复路径

### 9.4 外部评估者能知道后续投入点

即能明确看到：

- 如果要继续往商用走，还差什么工作

## 10. 一句话总结

如果说：

- `v8.0` 解决的是“仓库像一个公开项目”
- `v8.1` 解决的是“格式像一个有边界的项目”
- `v8.2` 解决的是“测试和恢复像一个有矩阵的项目”
- `v8.3` 解决的是“demo 像一个可执行产品入口”

那么：

```text
v8.4 解决的是：
让 CRYEXTS 第一次像一个“可以被认真拿去做商用前评估”的项目
```
