# CRYEXTS v8.0 设计说明

## 1. v8.0 的定位

`Version 8` 已经被定义成：

```text
发布工程化与评估工程化版本
```

而 `v8.0` 是这个大版本的第一步。

它不负责继续增加新的磁盘结构，
也不负责继续扩展新的文件系统语义，
而是专门解决一个最现实的问题：

```text
当前仓库已经能跑很多能力，
但还没有整理成一个适合公开展示、公开协作、公开评估的开源仓库基线
```

一句话定义：

```text
v8.0 = CRYEXTS 的 open-source baseline
```

## 2. 为什么现在先做 v8.0

到 `v7.3` 为止，项目已经具备：

- `Version 6 MVP` 的核心能力
- `Version 7` 的 multi-GDT 和 USB / raw-device demo 主线

但是当前仓库仍然存在一个明显问题：

### 2.1 `README.md` 仍然停留在早期阶段叙事

当前根目录 [README.md](/D:/Carl/cryptext4/cryexts/README.md:1) 还是以：

- `Phase 1`
- `Phase 2`
- `Phase 3`
- `Phase 4`

这种早期演进方式为主。

它的问题不是“内容错了”，而是：

- 不能快速告诉外部读者项目当前到了哪里
- 没有明确风险边界
- 没有明确支持范围
- 没有明确推荐入口
- 没有把 `Version 6 / Version 7` 主线收口成一个现代入口

### 2.2 仓库缺少几个公开项目的基础文件

当前仓库根目录还没有：

- `LICENSE`
- `CONTRIBUTING.md`
- `SECURITY.md`
- `ROADMAP.md`

这意味着：

- 外部读者不知道代码如何授权
- 外部贡献者不知道怎么参与
- 外部使用者不知道怎么报告安全问题
- 外部评估者不知道项目后续路线

### 2.3 当前项目边界还主要散落在各份文档中

现在很多关键边界已经在 `doc/` 里出现了，
比如：

- USB demo 风险
- 可商用评估但不是 production-ready
- 版本路线

但它们还没有收口成仓库根部的一套“公开口径”。

所以 `v8.0` 的目标很明确：

```text
不是发明新能力
而是把已有能力整理成一个像样的开源项目入口
```

## 3. v8.0 主目标

`v8.0` 建议只做下面一件事：

```text
建立 CRYEXTS 的开源仓库基线资料包
```

拆开就是五个交付物：

- 重写 `README.md`
- 新增 `LICENSE`
- 新增 `CONTRIBUTING.md`
- 新增 `SECURITY.md`
- 新增 `ROADMAP.md`

这五份文件就是 `v8.0` 的最小闭环。

## 4. v8.0 不做什么

为了防止范围继续发散，`v8.0` 明确不做：

- 新的 on-disk feature
- 新的 journal 格式
- 新的 extent 层级
- 新的加密方案
- 新的 allocator 算法
- 大规模性能优化
- 复杂 benchmark 系统

原因很简单：

```text
仓库入口还没整理清楚时，
继续加 feature 只会让开源发布更乱。
```

## 5. v8.0 要新增/重写的文件

## 5.1 `README.md`

### 功能定位

- 仓库首页入口
- 第一个被看到的文档
- 对外统一口径

### 当前问题

- 还偏“开发过程记录”
- 不够像“当前项目说明书”

### v8.0 目标结构

建议新 `README.md` 至少包含下面这些章节：

1. 项目简介
2. 当前定位
3. 已实现能力概览
4. 当前不承诺的能力
5. 构建环境
6. 快速开始
7. 推荐 smoke 入口
8. image / raw-device demo 入口
9. 风险声明
10. 文档导航
11. 路线图入口

### 需要明确写死的口径

必须明确写清楚：

```text
CRYEXTS 当前适合：
- 研究
- 教学
- 实验
- 专用测试设备

CRYEXTS 当前不建议：
- 重要生产数据
- 无备份设备
- 长期业务数据承载
```

### 目标

让第一次访问仓库的人在 1 分钟内知道：

- 这是个什么项目
- 现在能做什么
- 风险在哪
- 怎么最快跑起来

## 5.2 `LICENSE`

### 功能定位

- 定义仓库的代码授权方式

### 当前背景

源码里有：

```c
MODULE_LICENSE("GPL");
```

这说明内核模块语境下已经偏向 GPL 口径。

### v8.0 设计要求

- 仓库根目录必须有明确许可证文件
- 文档里必须统一许可证口径
- 后续第三方依赖说明要能和许可证一致

### 设计建议

如果没有额外商业授权方案，
最简单也最自然的路径就是：

```text
先采用 GPL 系列许可证口径与内核模块语义保持一致
```

这里 `v8.0` 的任务不是做复杂法律设计，
而是先把“没有 license 文件”的状态结束掉。

## 5.3 `CONTRIBUTING.md`

### 功能定位

- 约束外部协作方式
- 降低协作成本

### 应包含内容

建议至少包含：

1. 如何构建
2. 如何运行 smoke
3. 提交代码前要做什么
4. commit message 的基本约定
5. 文档更新要求
6. 版本开发方式
7. issue / PR 的基本范围

### 特别要写清楚的规则

- 新版本开发优先补文档
- 新增能力必须附 smoke
- 高风险修改必须带恢复/校验说明
- 不要直接把实验性质改动伪装成“已稳定能力”

### 目标

让以后别人提 PR 时，不需要靠口头约定。

## 5.4 `SECURITY.md`

### 功能定位

- 定义安全问题如何报告
- 定义当前项目的安全边界

### 为什么必须有

因为 CRYEXTS 已经涉及：

- 文件系统
- 原始块设备
- 加密
- 恢复

这些都属于容易被误解成“生产可用”的领域。

### 应包含内容

建议至少包含：

1. 支持的安全报告渠道
2. 不要公开发真实 exploit 的建议
3. 当前不承诺的安全级别
4. 加密实现当前的现实定位
5. 原始设备使用风险

### 必须写清楚的口径

```text
当前项目包含加密与恢复能力，
但这不等于已经完成生产级安全审计。
```

这句必须非常明确。

## 5.5 `ROADMAP.md`

### 功能定位

- 提供外部可理解的版本路线
- 告诉读者“项目接下来做什么”

### 内容来源

这个文件不需要重新发明路线，
直接收口已有版本规划即可。

也就是说，优先复用：

- [doc/cryexts-version-roadmap-to-usb-demo.md](/D:/Carl/cryptext4/cryexts/doc/cryexts-version-roadmap-to-usb-demo.md:1)
- [doc/cryext_8_requirements.md](/D:/Carl/cryptext4/cryexts/doc/cryext_8_requirements.md:1)

### 建议结构

1. 当前状态
2. 已完成里程碑
3. 当前大版本目标
4. 下一阶段计划
5. 非目标

### 目标

给外部读者一个短版本路线，而不是要求他先读完整个 `doc/`。

## 6. v8.0 的文档关系

`v8.0` 不应该再发明一套新的技术文档体系，
而应该把现有文档分成两层：

### 第一层：仓库根入口

- `README.md`
- `LICENSE`
- `CONTRIBUTING.md`
- `SECURITY.md`
- `ROADMAP.md`

### 第二层：技术细节沉淀

- `doc/cryext_8_requirements.md`
- `doc/cryext_7_requirements.md`
- `doc/cryexts-v7.3-change-notes.md`
- `doc/cryexts-version-roadmap-to-usb-demo.md`
- 其他版本文档

也就是说：

```text
根目录负责“告诉别人怎么看项目”
doc/ 负责“把技术细节讲透”
```

## 7. v8.0 的推荐实施顺序

建议按最小顺序落地：

1. 先重写 `README.md`
2. 再补 `LICENSE`
3. 再补 `CONTRIBUTING.md`
4. 再补 `SECURITY.md`
5. 最后补 `ROADMAP.md`

这个顺序的原因很简单：

- `README` 决定项目入口口径
- `LICENSE` 决定能不能公开发布
- `CONTRIBUTING/SECURITY` 决定协作边界
- `ROADMAP` 决定未来口径

## 8. v8.0 验收标准

`v8.0` 完成的最小标准建议定义为：

### 8.1 仓库根目录完整

根目录至少存在：

- `README.md`
- `LICENSE`
- `CONTRIBUTING.md`
- `SECURITY.md`
- `ROADMAP.md`

### 8.2 README 可独立说明项目

只看 `README.md`，一个陌生读者就能知道：

- 项目定位
- 主要能力
- 快速开始
- 风险边界
- 推荐测试入口

### 8.3 风险边界对外一致

仓库内不再出现互相冲突的表述，例如：

- 一处说“适合生产”
- 一处又说“仅实验使用”

`v8.0` 要把这类口径统一掉。

### 8.4 路线对外可理解

外部读者能看懂：

- 为什么先有 `Version 6`
- 为什么 `Version 7` 重点做 multi-GDT
- 为什么 `Version 8` 重点做发布与评估工程化

## 9. 一句话总结

如果说：

- `v7.x` 解决的是“文件系统可以在真实设备路径上跑起来”

那么：

```text
v8.0 解决的是：
这个项目第一次具备一个像样的开源仓库入口
```
